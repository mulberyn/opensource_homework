## 一、选择题

### 1.1 数据库的备份、恢复模式

**答案：A、B、D**

- **A 对**：这是**物理备份 + PITR（时间点恢复）**的标准模型：先有一份**基础备份**（base backup），
  再重放其后的**增量数据**（WAL 归档），就能把数据库恢复到任意时刻，或者追到最新。
  `pg_basebackup` + `recovery_target_*` 就是这套东西。
- **B 对**：备份确实分逻辑、物理两种：
  - **逻辑备份**：`pg_dump`，导出的是 SQL 或 COPY 数据，只关心"数据本身"，不管页怎么排、文件怎么分；
  - **物理备份**：`pg_basebackup` / 文件系统快照，备份的是文件与页的基础存储格式。
- **C 错**："逻辑备份、物理备份不可通用"太绝对。两者不能"互换格式"，但**能互相配合**（见 D）。
- **D 对**：典型配合方式是：物理基础备份 + WAL 归档做主恢复手段，逻辑备份用于跨版本迁移、
  单表恢复、审计留档。两者是互补的，不是互斥的。

### 1.2 磁盘 I/O 全被阻塞时，一条 UPDATE 的命运

**答案：D（以上都不对。Update 执行成功）**

关键在于**UPDATE 语句本身的写路径**：

```text
UPDATE tab SET col = val WHERE id = 1;
  1. 页在 shared buffer 里 → 直接改内存中的页（脏页）
  2. 生成 WAL record → 写进 WAL Buffer（还是内存）
  3. 返回 "UPDATE 1"
```

**执行阶段完全不碰磁盘**（前提是目标页已经在 shared buffer 里）。所以哪怕所有磁盘 I/O 都被阻塞，
这条 UPDATE 仍然能执行成功并返回。

- A 错：改的是内存里的页，不会因为"无法写表数据文件"而失败；
- B 错：WAL record 先进 WAL Buffer，`COMMIT` 才要求落盘；
- C 错：两条写都还没发生。

**补充两点边界情况**（这样答才完整）：

| 情况 | 结果 |
| --- | --- |
| 目标页不在 shared buffer | UPDATE 会**阻塞**在"读页"上，直到 I/O 恢复。是**卡住**，不是失败 |
| 执行完 UPDATE 后 `COMMIT` | COMMIT 要等 WAL 落盘，会**阻塞**；I/O 恢复后提交成功 |
| 磁盘永久损坏 | 此时才会失败（在 I/O 报错时） |

所以"执行成功"指的是**语句本身**，提交是另一件事——这正好是下一题（1.3 D）和 2.1 的核心。

### 1.3 数据库正常运行期间会触发 I/O 的操作

**答案：A、B、C、D（全选）**

| 选项 | 触发时机 | 说明 |
| --- | --- | --- |
| A | SELECT 要的页不在 buffer | 触发**读** I/O，把页读进 shared buffer |
| B | DML 要改的页不在 buffer | 同样先**读**进来才能改（"读-改-写"） |
| C | 脏页需要写回 | 由 **checkpoint** 或 **bgwriter** 触发**写** I/O，把脏页写回存储 |
| D | COMMIT | 必须等 **WAL 落盘**（`fsync`）完成后，提交才能返回成功 |

四类都是"正常运行"就会发生的，不需要故障。

### 1.4 关于 WAL，正确的有

**答案：A、B、D**

- **A 对**：这是 write-ahead 的定义——**块的修改必须先有对应的 WAL 记录**，然后才能改块。
  代码上体现为 `heap_update()` 里"调用 `log_heap_update()` 产生 WAL"在"页标脏"之前/同时。
- **B 对**：WAL 是**一条全局有序的日志流**，LSN 就是"日志流里的位置"。
  因为它严格追加，所以"LSN 小"就意味着"发生得早"，这天然构成一种**时间机制**
  （PITR、`pg_current_wal_lsn()`、恢复目标都是靠它）。
- **C 错**："WAL 日志没有缓存，所有修改必须直接落盘"完全反了。
- **D 对**：WAL 有 **WAL Buffer**（共享内存）。DML 执行时只把 WAL record 写进 WAL Buffer，
  **不要求立即落盘**；只有 `COMMIT`（以及 checkpoint、WAL 段切换）才要求"WAL 已落盘"。
  这正是 1.2 题 D 的原因，也是性能的关键：多个事务的 WAL 可以攒在一起一次 `fsync`（group commit）。

### 1.5 数据库体系结构简图，正确的选项

**答案：A、D**

- **A 对**：数据缓存（shared buffer）是**共享内存**，多进程共用同一段地址空间
  （`ShmemInitStruct` 分配，所有 backend 通过同一块映射访问）。
- **B 错**：WAL Buffer 不是"每进程私有"，它也在共享内存里（每个实例一份）。
- **C 错**：WAL Buffer 不是用 PG 的 **Memory Context** 分配的。Memory Context 是
  **backend 私有**的内存管理机制（`palloc`），而 WAL Buffer 属于共享内存
  （`ShmemInitStruct` + `LWLock` 保护）。
- **D 对**：数据缓存和 WAL Buffer **都是共享内存**。

### 1.6 图中红色箭头 1、2、3、4

图（`UPDATE tab SET col = val WHERE id = 1`）里：

```text
1: 新值 → WAL Buffer          （内存级：写日志）
2: 新值 → 数据缓存中的页        （内存级：改数据页）
3: WAL Buffer → XLOG 文件      （存储级：日志落盘）
4: 页 → 表数据文件             （存储级：数据落盘）
```

**答案：B、C**

- **B 对**："1 与 2"说明在内存这一级，**WAL Buffer 的写早于数据页的修改**——
  先有日志记录，才允许改页（这就是 write-ahead 在内存层面的体现）。
- **C 对**："3 与 4"说明在存储这一级，**WAL 的落盘必须早于数据页的落盘**——
  如果数据页先落盘、日志后落盘，中间崩溃就没有日志可以重放，数据就坏了。
- **D 错**：说"1、2、3、4 只是举例，并无实际意义"是不对的，这个顺序是**正确性要求**，不是画图习惯。
- **关于 A**：A 说"1、2 在前，3、4 在后，说明要先写内存，再存储落盘"——这个**现象描述本身成立**
  （内存操作确实先发生），但它不是在说 WAL 的规则；本题的考点是"谁先谁后"这条**约束**，
  所以答案取 B、C。

## 二、问答分析题

### 2.1 为什么一定要"WAL 的写早于数据文件的写"

#### （1）先看直觉：不写 WAL、直接写数据文件，会怎样

假设一个事务改了 100 个页，直接往数据文件写。会遇到五个问题：

| 问题 | 说明 |
| --- | --- |
| **随机写** | 数据页在磁盘上分散，100 个页 = 100 次随机寻道；而 WAL 是**顺序追加** |
| **无法合并** | 不同页的写没法合并成一个 I/O；而 WAL 里多个事务的记录可以塞进同一个 WAL 页，一次落盘 |
| **原子性无法保证** | 100 个页写到第 50 个时崩溃，前 50 个已改、后 50 个没改，数据处于**撕裂状态**（半事务） |
| **页撕裂（torn page）** | 8 KB 的页可能只写进去 4 KB（掉电、坏扇区），剩下的部分是垃圾，页本身不可解析 |
| **fsync 次数爆炸** | 要保证持久性，每个页都得 `fsync`；WAL 只需要对"日志流末尾"`fsync` 一次 |

这五条里，**"原子性"和"页撕裂"是致命的**：一旦发生，数据库可能再也起不来。

#### （2）WAL 的解法：把"随机、多次、不可合并"的写，变成"顺序、一次、可合并"的写

WAL 的核心思路只有一句：

> **先把"改了什么"顺序记下来（日志），数据页可以晚点再慢慢写（checkpoint）。**

于是：

1. **写放大大幅降低**：一个事务改 100 个页 → 100 条 WAL record 顺序追加（可能只占几 KB），
   数据页的随机写被推迟、被合并、被摊平到 checkpoint；
2. **一次 fsync 覆盖多个事务**：多个并发事务的 WAL 攒在 WAL Buffer 里，`COMMIT` 时一起 `fsync`
   （group commit），吞吐量成倍提升；
3. **崩溃恢复有依据**：重启时从最近的 checkpoint 开始重放 WAL，把"已提交但数据页没写"的修改补上，
   丢掉"未提交"的修改；
4. **页撕裂有救**：`full_page_writes` 让每个 checkpoint 之后第一次修改某页时，
   把**整页**的前映像写进 WAL，恢复时先用整页覆盖，避开半写页的问题。

#### （3）为什么"日志必须早于数据页"这条顺序不能破

这是 WAL 的**正确性前提**，用一个反例说明：

```text
t1: 修改页 P（内存）
t2: 页 P 被写回磁盘（P 变成新内容）
t3: 【崩溃】—— 此时 WAL 记录还没落盘
```

重启后：磁盘上 P 是**新内容**，但日志里**没有**这次修改的记录。
恢复过程"重放日志"补不上任何东西，数据库认为这次修改从未发生——
可数据页已经是新的了。**数据与日志不一致，且无从修复。**

反过来，"日志先落盘、数据页后落盘"：

```text
t1: WAL record 落盘（顺序写，fsync）
t2: 修改内存页
t3: checkpoint 时页写回磁盘
t4: 【崩溃】—— 页可能只写了一半
```

重启后：日志里有完整记录 → 重放 → 页被重建成正确内容。**任何时刻崩溃都能恢复。**

一句话：**日志是"事实"，数据页只是"事实的物化"。物化可以晚、可以重做，但事实不能丢。**

#### （4）用本机实验验证这条规则

我直接在 openHalo 上做了实验，用 `hexdump` 看**磁盘上的真实字节**（不是查系统表）。

**准备**：建表、插两行、checkpoint，此时磁盘页里有两个版本，`t_xmax` 都是 0：

```text
=== [0] checkpoint 完成，磁盘页内容 ===
00001fc0  02 00 03 00 02 08 18 00  02 00 00 00 0f e6 9d 8e  |................|
00001ff0  01 00 00 00 0f e5 bc a0  e4 b8 89 00 e8 03 00 00  |................|
```

> 题外话：第一次 `hexdump` 时我看到的是**全零**——因为数据只在 shared buffer 里、还没落盘。
> 必须 `checkpoint` 之后磁盘文件才有内容。

**执行 UPDATE（不提交）**：

```sql
begin;
update t1 set balance = balance - 100 where id = 1;

 lsn_before | lsn_after_update | wal_bytes
------------+------------------+-----------
 0/32F4DE0  | 0/32F4DE0        |         0
```

注意 `wal_bytes = 0`：`pg_current_wal_lsn()` 返回的是**已写出（write）的位置**，
而这条 UPDATE 的 WAL record 还躺在 **WAL Buffer** 里，没写出去。磁盘上的页也**完全没变**。

**COMMIT 之后**：

```sql
commit;
 lsn_after_commit | commit_wal_bytes
------------------+------------------
 0/32F4EE8        |              264
```

提交时 WAL 被刷出，写位置前进了 **264 字节**。但此时磁盘上的页**仍然是旧内容**：

```text
=== [2] 已 COMMIT，但 checkpoint 之前磁盘页仍是旧内容 ===
00001fc0  02 00 03 00 02 08 18 00  02 00 00 00 0f e6 9d 8e  |................|
```

**而内存中的页已经是新状态**（`pageinspect` 读的是 buffer）：

```text
 lp | t_xmin | t_xmax | t_ctid | t_infomask
----+--------+--------+--------+------------
  1 |    762 |    763 | (0,3)  |        258     ← 旧版本，被打上 xmax=763
  2 |    762 |      0 | (0,2)  |       2306     ← 没动
  3 |    763 |      0 | (0,3)  |      10242     ← 新版本，balance 从 1000 变成 900
```

**CHECKPOINT 之后**，新版本才写进数据文件：

```text
=== [3] checkpoint 之后，新版本才被写进数据文件 ===
00001fd0  e5 9b 9b 00 10 27 00 00  fa 02 00 00  fb 02 00 00  |.....'..........|
00001fe0  00 00 00 00 00 00 00 00  03 00 03 40 02 01 18 00  |...........@....|
00001ff0  01 00 00 00 0f e5 bc a0  e4 b8 89 00 e8 03 00 00  |................|
```

**这个实验完整地展示了四件事**：

1. UPDATE 只改内存（1.2 题的答案）；
2. WAL record 先进 WAL Buffer，`COMMIT` 才刷出（1.4 题 D）；
3. **WAL 已经落盘了，数据页还没落盘**——这就是"日志早于数据页"的直观证据；
4. 数据页什么时候写由 `checkpoint`/bgwriter 决定，与事务提交解耦。

#### （5）如果把顺序反过来，能不能"少写一次"

有人会问：既然数据页早晚要写，为什么不干脆"改完就写页、不写日志"？

因为那样就回到了（1）的五个问题。而且**日志的写比数据页便宜得多**：

| | 数据页写 | WAL 写 |
| --- | --- | --- |
| 访问模式 | 随机（页散落在整个文件） | 顺序（追加到日志末尾） |
| 能否合并 | 不同页不能合并 | 多个事务的记录可以合并进一个 WAL 页 |
| 一次 fsync 覆盖 | 一个页 | 一批事务 |
| 崩溃后能否恢复 | 不能（没有前映像） | 能（重放日志） |

所以"多写一份日志"不是浪费，而是**用最便宜的写，换取正确性和性能**。
这也解释了课件里那句话：**"数据文件的写是随机的，WAL 日志的写是顺序的"**。

#### （6）代价与权衡（这样才算完整）

WAL 不是没有成本：

1. **额外写放大**：每次修改至少多写一份日志；`full_page_writes` 还会在 checkpoint 后首改时写整页；
2. **checkpoint 抖动**：checkpoint 要把大量脏页刷出去，可能造成 I/O 尖峰
   （所以有 `checkpoint_completion_target` 来摊平）；
3. **日志空间**：WAL 会持续增长，需要归档/清理策略（`max_wal_size`、归档）；
4. **恢复时间**：日志越长，崩溃恢复越久（`min_wal_size`/checkpoint 频率是权衡）。

但这些代价，与"数据不一致、库起不来"相比，完全可以接受。

#### （7）一句话总结

> **数据页是"随机、不可合并、不可重放"的写；WAL 是"顺序、可合并、可重放"的写。**
> 数据库用后者作为"事实来源"，把前者降级为"可以晚点做、可以重做"的物化动作。
> 因此 **WAL 必须先落盘**——否则"事实"丢了，而"物化"却已经发生，数据就再也对不上了。

## 四、思考

这门课的两次作业（0924 的 PMC、1105 的 WAL）其实是同一个主题的两面：

- **0924** 让我看到"性能的真相藏在硬件里"——同样的代码，访存模式不同，代价能差 80 倍；
- **1105** 让我看到"正确性的真相藏在顺序里"——同样两个写，顺序不同，一个可恢复、一个彻底坏掉。

数据库之所以难，就在于它必须同时把这两件事做到极致：
**既要让每一次 I/O 尽量顺序、尽量少，又要让任何时刻崩溃都能恢复。**
WAL + checkpoint + MVCC 这一整套设计，本质上都是在"性能"与"正确性"之间找那个可证明的平衡点。
