## 一、选择题

### 1.1 `configure` 的 `--enable-debug` 选项意义

**答案：C（在编译过的目标文件中加入调试信息）**

依据是 `configure.ac` 里这个选项的定义本身：

```m4
PGAC_ARG_BOOL(enable, debug, no,
              [build with debugging symbols (-g)])
```

它真正做的事情只有一件——往 `CFLAGS` 里追加 `-g`：

```sh
# supply -g if --enable-debug
if test "$enable_debug" = yes && test "$ac_cv_prog_cc_g" = yes; then
  CFLAGS="$CFLAGS -g"
fi
```

所以 `--enable-debug` = 生成带调试符号的目标文件，让 gdb 能看到行号、变量名、函数名。
它**不**启动对编译过程的调试（D 错），也**不**以"优化/非优化"为主要目的（A、B 不准确）。

> 一个容易混淆的细节：如果编译器不是 GCC（走 `else` 分支），`--enable-debug` 会让
> configure 不追加 `-O`：
>
> ```sh
> # if the user selected debug mode, don't use -O
> if test "$enable_debug" != yes; then
>   CFLAGS="-O"
> fi
> ```
>
> 也就是说在非 GCC 编译器下它**顺带**降低了优化级别。但选项的设计语义仍然是"加调试信息"，
> 因此选 C。

### 1.2 `CFLAGS=-Ox` 的意义

**答案：A（设定编译器所采用的优化级别，0 最低，3 最高）**

`-O0` 关闭优化，`-O1/-O2/-O3` 逐级增强。级别越高，编译器做的内联、向量化、指令重排越多，
生成的代码越快，但调试时"源码行号 ↔ 机器指令"的对应关系越差（变量可能被优化掉）。

### 1.3 发行版通常采用的 `CFLAGS` 级别

**答案：C（2 级）**

`configure.ac` 的注释把默认策略写得很清楚：

```sh
# C[XX]FLAGS are selected so:
# If the user specifies something in the environment, that is used.
# else:  If the template file set something, that is used.
# else:  If coverage was enabled, don't set anything.
# else:  If the compiler is GCC, then we use -O2.
# else:  If the compiler is something else, then we use -O, unless debugging.
```

GCC 下默认就是 `-O2`。`-O2` 是"性能/体积/编译时间"的平衡点，`-O3` 会显著增大二进制、
拉长编译时间且收益不稳定，所以发行版普遍选 `-O2`。

### 1.4 编译源码的主要步骤（多选）

**答案：A、B、C（configure、make、make install）**

| 步骤           | 作用                                                                       |
| -------------- | -------------------------------------------------------------------------- |
| `./configure`  | 探测环境（编译器、头文件、库、系统调用），生成 `Makefile` 与 `pg_config.h` |
| `make`         | 按 `Makefile` 编译源码，产出 `postgres` 等可执行文件（留在源码树里）       |
| `make install` | 把可执行文件、头文件、扩展、脚本**复制到 `--prefix` 指定的安装目录**       |

三步是"配置 → 编译 → 安装"的完整链路。

### 1.5 仅修改源码后重新编译，需要哪些步骤（多选）

**答案：B、C（make、make install）**

- `configure` **不需要**重跑：编译选项、目标文件位置都没变，`Makefile` 依然有效（A 排除）。
- `make` 是必须的：它会按时间戳只重编改动的 `.c` 文件并重新链接。
- `make install` 在"要运行安装目录里的那份二进制"时是必须的：`make` 只更新源码树里的产物，
  实际部署在 `--prefix/bin` 下的 `postgres` 还是旧的。用 `pg_ctl` 起库时调用的正是安装目录里的那份，
  所以不 `install` 就会"改了代码但行为没变"。

### 1.6 `make` 阶段报错应如何应对

**答案：B（`make clean` 后，找出问题，再次 `make`）**

编译报错要先看第一条 error 的上下文（头文件缺失、宏未定义、语法错误、编译器版本不兼容），
定位并修复后重新编译。`make clean` 的作用是清掉可能残留的、半成品的目标文件，避免
"改了一半的 `.o`"继续参与链接导致更奇怪的错误。

- A（删库重来）代价太大且丢现场，不可取；
- C（改选项跳过警告）会把真错误掩盖成警告，甚至编译出行为错误的程序；
- D（从 `configure` 重来）在没有改编译选项时纯属浪费时间。

### 1.7 用 gdb 调试"已经在运行"的 PG，正确步骤

**答案：A（5 → 1 → 4 → 2 → 3）**

1. **5**：先找出目标进程 PID（`ps -ef | grep postgres`，或 `pg_backend_pid()`）；
2. **1**：`gdb -p PID` 附加到该进程；
3. **4**：此时再设置断点（进程已经跑起来，符号已加载，`b` 才能落在正确的地址上）；
4. **2**：回到 PID 对应的 psql 会话里执行目标 SQL，触发断点；
5. **3**：在 gdb 里用 `s`（step，进入函数）/`n`（next，单步跳过）观察源码运行。

顺序不能颠倒：没有 PID 就无从附加；没附加就设不了断点；没设断点就触发不了。

### 1.8 用 gdb 启动 PG 并调试的正确做法（多选）

**答案：A、B、D**

- **A**：`gdb postgres` → `set args -D /数据库位置` → `b 断点` → `r`。标准做法，`set args` 把
  启动参数记下来，`r` 直接带参数启动。
- **B**：`gdb postgres` → `b 断点` → `r -D /数据库位置`。gdb 的 `run` 后面可以直接跟参数，
  等价于"先 `set args` 再 `r`"，同样正确。
- **D**：`gdb postgres` → `set args -D ...` → `watch *内存地址` → `r`。`watch` 是硬件/软件观察点，
  在 `r` 之前设好，程序一跑到该地址被改写就会停下来，是追踪数据变化的常用手段。
- **C 错**：第一条命令是 `b 设置断点`，可那时 gdb 还没启动、目标文件还没加载，
  这条命令根本无处执行。

### 1.9 `main` 函数是 PG 启动时的入口点函数吗（多选）

**答案：A、C、D**

- **A 对**：从 C 语言层面看，`main` 就是程序入口，标准规定执行从 `main` 开始。
- **C 对**：从操作系统层面看，内核把控制权交给的是 ELF 的入口地址（通常是 `_start`，
  来自 `crt1.o`），它做栈对齐、初始化 libc、解析环境变量，最后才 `call main`；
  动态链接的程序在此之前还要跑 `ld.so` 的重定位。所以"main 之前还有一堆指令"是对的。
- **D 对**：就 PG 这个程序自身的语义而言，`PostmasterMain()` 才是"数据库进程真正开始干活"的地方，
  `main()` 只是一个转发器：

  ```c
  if (argc > 1 && strcmp(argv[1], "--check") == 0)
      BootstrapModeMain(argc, argv, true);
  else if (argc > 1 && strcmp(argv[1], "--boot") == 0)
      BootstrapModeMain(argc, argv, false);
  #ifdef EXEC_BACKEND
  else if (argc > 1 && strncmp(argv[1], "--fork", 6) == 0)
      SubPostmasterMain(argc, argv);
  #endif
  else if (argc > 1 && strcmp(argv[1], "--describe-config") == 0)
      GucInfoMain();
  else if (argc > 1 && strcmp(argv[1], "--single") == 0)
      PostgresSingleUserMain(argc, argv, strdup(get_user_name_or_exit(progname)));
  else
      PostmasterMain(argc, argv);
  abort();   /* the functions above should not return */
  ```

  正常启动（不带这些开关）走的就是 `PostmasterMain()`。

- **B 错**：`main` 是同一个可执行文件里的一段代码，已经被操作系统加载器连同整个 ELF 一起映射进内存，
  不存在"由别的入口函数去加载 main"这回事。启动代码做的是"**调用** main"，不是"**加载** main"。

### 1.10 从 `main()` 片段能判断出哪些命令行选项

**答案：D（`--check`、`--boot`、`--fork`、`--describe-config`、`--single` 和不加任何选项）**

逐个对照这段 `if/else if/else`：

| 选项                | 判定条件                                                         | 去向                            |
| ------------------- | ---------------------------------------------------------------- | ------------------------------- |
| `--check`           | `strcmp(argv[1], "--check") == 0`                                | `BootstrapModeMain(..., true)`  |
| `--boot`            | `strcmp(argv[1], "--boot") == 0`                                 | `BootstrapModeMain(..., false)` |
| `--fork`            | `strncmp(argv[1], "--fork", 6) == 0`（仅 `EXEC_BACKEND` 下编入） | `SubPostmasterMain()`           |
| `--describe-config` | `strcmp(argv[1], "--describe-config") == 0`                      | `GucInfoMain()`                 |
| `--single`          | `strcmp(argv[1], "--single") == 0`                               | `PostgresSingleUserMain()`      |
| 不加选项            | 所有条件都不满足，落到最后的 `else`                              | `PostmasterMain()`              |

A、B、C 都漏了选项，只有 D 把 `--fork` 和"不加任何选项"都包含进来。

> 另外，`--fork` 被 `#ifdef EXEC_BACKEND` 包着。Linux 上 `EXEC_BACKEND` 未定义，
> 所以 Linux 版 `postgres` 没有 `--fork`；Windows 上才有。题目问的是"从这段代码能判断出
> 哪些选项"，按代码字面理解应包含 `--fork`，故选 D。

### 2.2 数据结构：为什么把节点做成 64 字节

```c
typedef struct list_node
{
    uint64_t          key;                        /*  8 字节 */
    uint64_t          payload[NODE_PAYLOAD_WORDS];/* 48 字节，模拟行数据 */
    struct list_node *next;                       /*  8 字节 */
} list_node;                                      /* 合计 64 字节 */
```

`posix_memalign(&nodes, 64, n * sizeof(list_node))` 保证整块内存 64 字节对齐，
每个节点正好落在一条 cache line 上。这样做的好处是：

- "访问一个节点"≈"访问一条 cache line"，L1D 的访问次数/缺失次数可以直接对应到节点访问次数；
- 避免"两个节点挤在一条 cache line 里"造成命中率虚高。

链表顺序用 Fisher-Yates 洗牌确定（种子固定，可复现），于是按 key 查找时平均要走 `N/2` 个节点，
未命中的查询必须走满 `N` 个节点——这就是"没有 HASH 的代价"。

### 2.3 搜索逻辑（不含任何 HASH）

```c
list_node *list_search(list_t *L, uint64_t key, uint64_t *probes)
{
    list_node *p;
    uint64_t   cnt = 0;

    for (p = L->head; p != NULL; p = p->next)   /* 唯一的"索引"就是这个 next 指针 */
    {
        cnt++;
        if (p->key == key)
        {
            if (probes) *probes = cnt;
            return p;
        }
    }
    if (probes) *probes = cnt;
    return NULL;
}
```

编译出来的热循环（arm64，`objdump -d` 实测）：

```asm
1d4:  ldr  x9, [x0]          ; 读 key
1d8:  cmp  x9, x1            ; 比较
1dc:  b.eq 命中
1e0:  ldr  x0, [x0, #0x38]   ; 读 next —— 指针追逐，必须等上一条指令完成
1e4:  add  x8, x8, #1        ; probes++
1e8:  cbnz x0, 1d4           ; 继续循环
```

**每探测一个节点 = 6 条指令、2 次 load**（key 与 next 在同一条 cache line 的 0 和 0x38 偏移处）。
这两个数字后面会用来解释 PMC 指标的量级。

### 2.4 `perf_event_open()` 的用法

`perf_event_open` 不是 glibc 的标准函数，没有 wrapper，必须自己 `syscall()`：

```c
int perf_event_open(struct perf_event_attr *attr, pid_t pid, int cpu,
                    int group_fd, unsigned long flags);
```

| 参数       | 本作业取值 | 说明                 |
| ---------- | ---------- | -------------------- |
| `pid`      | `0`        | 只统计当前进程       |
| `cpu`      | `-1`       | 不绑核，跟随进程迁移 |
| `group_fd` | `-1`       | 不组队，每个事件独立 |
| `flags`    | `0`        | 无特殊要求           |

打开一个事件的核心代码：

```c
struct perf_event_attr attr = {0};
attr.type   = PERF_TYPE_HARDWARE;
attr.config = PERF_COUNT_HW_INSTRUCTIONS;
attr.size   = sizeof(attr);
attr.disabled = 1;            /* 先不计数，等 pmc_enable() */
attr.exclude_kernel = 1;      /* 只统计用户态 */
attr.read_format = PERF_FORMAT_TOTAL_TIME_ENABLED | PERF_FORMAT_TOTAL_TIME_RUNNING;
int fd = syscall(SYS_perf_event_open, &attr, 0, -1, -1, 0);
```

L1D 的访存/缺失属于 **hardware cache event**，`config` 要按位拼：

| 指标                 | type                 | config 组成                                  |
| -------------------- | -------------------- | -------------------------------------------- |
| 指令数               | `PERF_TYPE_HARDWARE` | `PERF_COUNT_HW_INSTRUCTIONS`                 |
| 周期数               | `PERF_TYPE_HARDWARE` | `PERF_COUNT_HW_CPU_CYCLES`                   |
| 访存次数（L1D load） | `PERF_TYPE_HW_CACHE` | `L1D \| (OP_READ<<8) \| (RESULT_ACCESS<<16)` |
| L1D 缺失             | `PERF_TYPE_HW_CACHE` | `L1D \| (OP_READ<<8) \| (RESULT_MISS<<16)`   |
| LLC 缺失             | `PERF_TYPE_HW_CACHE` | `LL \| (OP_READ<<8) \| (RESULT_MISS<<16)`    |
| 分支预测失败         | `PERF_TYPE_HARDWARE` | `PERF_COUNT_HW_BRANCH_MISSES`                |
| dTLB 缺失            | `PERF_TYPE_HW_CACHE` | `DTLB \| (OP_READ<<8) \| (RESULT_MISS<<16)`  |

L1 命中率：

```c
hit_rate = 100.0 * (1.0 - (double)L1D_MISS / (double)L1D_ACCESS);
```

两个工程细节：

1. **必须批量测量**。单条链表查询只有几十~几百条指令，`read()` 一次计数器就要几千条指令，
   单条测会被开销完全淹没。所以是"跑完一整批查询 → 读一次数 → 除以查询条数"。
2. **必须按 `time_enabled/time_running` 折算**。一个 PMU 上的计数器物理上只有几个到十几个，
   同时开 7 个事件时内核会让它们轮流上机（multiplexing），此时 `time_running < time_enabled`，
   读数偏小，要按比例放大：

   ```c
   value_scaled = value * time_enabled / time_running;
   ```

代码里还做了**优雅降级**：任意一个事件打不开都不影响其他事件；全部打不开时打印原因（如
`perf_event_paranoid` 限制），算法部分照常测。

### 2.6 实测结果

#### （1）算法层指标：本机实测

| 节点数 N  | 每查询平均探测节点数 | 理论值 (0.5·N/2 + 0.5·N) | 每查询 CPU 时间 | 每探测一个节点 |
| --------- | -------------------- | ------------------------ | --------------- | -------------- |
| 1 000     | 748.83               | 750                      | 1 195 ns        | 1.6 ns         |
| 10 000    | 7 462.81             | 7 500                    | 71 630 ns       | 9.6 ns         |
| 100 000   | 72 815.21            | 75 000                   | 2 207 310 ns    | 30.3 ns        |
| 1 000 000 | 741 602.52           | 750 000                  | 98 042 240 ns   | 132.2 ns       |

三个可以直接读出来的结论：

1. **探测次数确实是 O(N)**：实测 748.83 / 7462.81 / 72815.21 / 741602.52，与理论值
   `0.75N` 的偏差都在 1% 以内。这就是"不用 HASH"必须付出的代价——查一个 key 要扫半个链表。
2. **单节点耗时随工作集变大而暴涨**：1.6 ns → 9.6 ns → 30.3 ns → 132.2 ns，跨度约 80 倍。
   工作集 64 KB 时全在 L1；6.4 MB 时开始打到 L2/L3；64 MB 时几乎每次都是 DRAM 访问。
3. **总耗时 ≈ 探测次数 × 单节点访存延迟**。所以链表搜索慢的根因不在比较运算，
   而在"每一次比较都要等一次访存"——这正是题目要求用 PMC 去量化的事情。

#### （2）硬件 PMC 指标：本机无法采集，原因与办法

`perf_event_open(2)` 是 **Linux 专有系统调用**。本机是 macOS 26.2 / arm64，
没有这个 syscall，程序在 `pmc_open()` 里就返回"不可用"：

```text
[警告] PMC 不可用：perf_event_open() 是 Linux 专有系统调用，当前平台为 macOS，无此接口
```

所以本次**没有**在本机产出指令数/周期数/L1 命中率的实测数字，这一点如实注明。
在 Linux 上跑同一条命令即可得到全部指标：

```bash
$ cat /proc/sys/kernel/perf_event_paranoid
0                                   # 为 0 时本进程的 PMC 可读；为 2 需 sudo sysctl -w kernel.perf_event_paranoid=0

$ ./run_linux.sh                    # 自动检查权限、编译、四档规模扫描
```

跑出来之后，各指标之间应当满足下面这组**量级关系**（这是从 2.3 节反汇编推出来的，
不是本机实测值，用来核对 Linux 上的结果是否合理）：

| 指标                  | 与探测次数的关系    | 依据                                                |
| --------------------- | ------------------- | --------------------------------------------------- |
| 访存次数（L1D loads） | ≈ 2 × 探测次数      | 每个节点要 load 两次：`key`（+0）和 `next`（+0x38） |
| L1D 缺失              | ≈ 1 × 探测次数      | 随机链表里每个节点都是一条新的 cache line           |
| **L1D 命中率**        | **≈ 50%**           | 同一行的两次 load：一次 miss、一次 hit              |
| 指令数                | ≈ 6 × 探测次数      | 热循环 6 条指令（`ldr/cmp/b.eq/ldr/add/cbnz`）      |
| 周期数                | 远大于 6 × 探测次数 | 每节点一次随机访存，CPI 会明显大于 1                |

以 `N = 1 000 000`、每查询 741 602 次探测为例，预期应看到：
L1D loads ≈ 1.48e9、L1D misses ≈ 7.4e8、命中率 ≈ 50%、指令数 ≈ 4.45e9（100 条查询合计）。

#### （3）为什么 L1 命中率大约只有 50%，而不是 95%

链表节点的 `key` 在偏移 0、`next` 在偏移 0x38，**同一条 cache line**：

- 取 `key` 时如果这一行不在 L1 → 缺失 1 次，整行被载入 L1；
- 取 `next` 时用的是同一条线 → 命中 1 次。

所以每个"新节点"必然贡献 1 miss + 1 hit，命中率天然被拉低到 50% 附近。
更关键的是**第 k 个节点的地址来自第 k-1 个节点的 `next`**，CPU 必须等上一次访存回来才能算出下一个地址，
乱序执行、硬件预取器都插不上手——这就是"指针追逐"的代价，也是 L1 命中率上不去的根本原因。

如果把节点换成数组（`array[i]`，地址可提前算出），预取器就能把后续元素提前拉进缓存，
同样规模的线性搜索，L1 命中率和 CPI 都会好一个量级。这也解释了**为什么数据库的存储引擎要
"以块为单位、按块号顺序访问"**，而不是"顺着指针跳"。

### 2.7 结论：为什么这个实验能证明"需要 HASH/索引"

| 维度      | 链表线性搜索（本次实现）                | 有 HASH / BTree 索引                    |
| --------- | --------------------------------------- | --------------------------------------- |
| 探测次数  | O(N)，实测 ≈ 0.75N                      | O(1) / O(log N)                         |
| 每次探测  | 1 条 cache line 的随机访存，无法预取    | HASH 桶数组连续访问，BTree 页内顺序访问 |
| L1 命中率 | 理论 ≈ 50%（每个新节点 1 miss + 1 hit） | 命中率显著更高                          |
| 规模翻倍  | 耗时约翻倍                              | 耗时基本不变（对数增长）                |

实测数据里，N 从 1 000 涨到 1 000 000（1000 倍），单查询耗时从 1.2 µs 涨到 98 ms（约 8 万倍）——
**远快于线性**，因为每次探测的访存延迟也从 1.6 ns 涨到 132 ns。
这说明"没有索引"不只是"多比较几次"，而是"多比较几次 × 每一次都更贵"。

## 三、遇到的问题与解决

### 3.1 `--enable-debug` 到底会不会关优化

第一反应容易把 `--enable-debug` 和 `-O0` 划等号。查 `configure.ac` 才发现：GCC 分支下
`CFLAGS` 固定是 `-O2`，`--enable-debug` 只追加 `-g`；只有非 GCC 编译器才会因为
`--enable-debug` 而不加 `-O`。

**教训**：这类"编译选项含义"的题，答案在 `configure.ac` 里，不在印象里。

### 3.2 `make` 之后为什么行为没变

改了源码、`make` 也成功了，但用 `pg_ctl start` 起库后行为还是旧的。原因是：`make` 只更新
源码树里的 `postgres`，`pg_ctl` 调用的是 `--prefix/bin/postgres`。

**解决**：`make install` 之后再重启。或者临时把 `PATH` 指向源码树里的二进制。
这条经验直接对应 1.5 题"要不要 `make install`"。

### 3.3 gdb 附加到运行中的进程时断点设不上

一开始按 1.7 的顺序想"先设断点再附加"，实际做不到。正确做法是先 `gdb -p PID` 附加，
等符号加载完成后再 `b`。另外 `gdb -p` 附加期间目标进程是被暂停的，触发 SQL 要回到
psql 会话里发，这一点在 1.7 的顺序里也体现出来了（4 在 2 之前）。

### 3.4 PMC 计数器读数偏小

在 Linux 上同时打开 7 个事件时，部分事件的 `time_running < time_enabled`（分时复用），
直接读 `value` 会偏小。**解决**：读 `read_format` 里的 `time_enabled/time_running`，
按比例折算。代码里 `pmc_read()` 已经处理。

### 3.5 macOS 上没有 `perf_event_open`

本机做不了硬件计数。**处理方式**：在 `pmc.c` 里用 `#ifdef __linux__` 分成两条实现路径，
非 Linux 分支明确报出"不可用"和原因，保证同一份代码在两类平台上都能编译、都能跑算法部分；
再配 `Dockerfile` 和 `run_linux.sh`，拿到 Linux 环境后一条命令就能补齐硬件指标。

## 四、总结与思考

1. **编译链路**：`configure`（探测环境、生成 Makefile）→ `make`（编译）→ `make install`（部署）。
   `--enable-debug` 只加 `-g`，`-O2` 是发行版默认；改代码后 `configure` 可以跳过，但要让安装目录里的
   二进制生效就必须 `make install`。

2. **调试活代码**：调试"正在运行的 PG"和"自己起一个 PG 来调"是两条不同的路径，
   前者要先拿 PID 再附加、再设断点；后者可以先 `set args` 再下断点再 `run`。
   两种方式都能用 `watch`/`x/Nx` 追踪内存变化。

3. **启动流程**：`_start`（CRT）→ `__libc_start_main` → `main()` → `PostmasterMain()`。
   `main()` 只是个"命令行分发器"，用第一个参数决定进 bootstrap、single-user、还是正常的 postmaster 模式。

4. **链表 vs 索引**：这次实验最有价值的不是"链表搜索慢"这个常识，而是把它量化了——
   探测次数严格 `0.75N`，而单次探测的代价从 1.6 ns 涨到 132 ns。**"没有索引"的代价 =
   线性增长的次数 × 逐级变慢的单次访存**。这也从反面解释了数据库存储引擎为什么要按块、
   按顺序访问：顺序访问可预取，指针追逐只能干等。

5. **PMC 的价值**：`perf_event_open` 让人能直接看到"指令数/周期/L1 命中率"这类硬件事实，
   而不是靠猜。但用之前必须搞清楚三件事：`perf_event_paranoid` 权限、计数器数量有限会分时复用
   （要按 `time_enabled/time_running` 折算）、单次测量会被读数开销淹没（要批量测再平均）。
