## 一、选择题

### 1.1 建一张 `varchar(30)` 的表插一行，表文件大小

**答案：C（8 KB）**

实测（openHalo 14.18）：

```sql
create table vage30 (c1 varchar(30));
insert into vage30 values('012345678901234567890123456789');

select pg_relation_size('vage30') as bytes, pg_size_pretty(pg_relation_size('vage30'));
 bytes |   pretty
-------+------------
  8192 | 8192 bytes
```

`8192 字节 = 8 KB`，正好是**一个页（block）**。原因：

1. PG 的存储单位是页，`block_size = 8192`（`show block_size` 实测），**表文件按页分配**，
   插入第一行就要占满一整页，不会按"实际用了多少字节"给文件；
2. 这一行本身只占 `55` 字节：行头 `23` 字节 + 对齐到 `t_hoff = 24` + `31` 字节数据
   （1 字节变长头 + 30 字节字符串）：

   ```text
   lp | lp_off | lp_len | t_xmin | t_xmax | t_ctid | t_data
    1 |   8136 |     55 |    753 |      0 | (0,1)  | \x3f303132...3839
   ```

   `0x3f = 0b00111111`，低位 1 表示"1 字节变长头"，`0x3f >> 1 = 31` 即变长字段总长 31 字节；
3. 页内其余 8136 - 28 ≈ 7.9 KB 全是空闲空间，但**文件大小不因此缩小**。

所以 A（"30 字节 + 几十字节管理数据"）是"数据的逻辑大小"，不是文件大小；B、D 与 8 KB 页不匹配。

### 1.2 关于执行器入口

**答案：D（`PortalRun()`）**

四个函数的定位完全不同：

| 函数 | 阶段 | 做了什么 |
| --- | --- | --- |
| `CreatePortal()` | 准备 | 分配 Portal 结构，给查询一个"运行句柄" |
| `PortalDefineQuery()` | 准备 | 把 parse tree、plan tree、query string 挂到 Portal 上 |
| `PortalStart()` | 准备 | 建立执行所需的快照、参数、`QueryDesc`，**还没真正取行** |
| `PortalRun()` | **执行** | 按 `FETCH_ALL` 之类的方式反复调用执行器，把结果交给 receiver |

`PortalRun()` 内部才走到 `ExecutorRun()` → `standard_ExecutorRun()` → `ExecutePlan()`，
然后才是 `ExecProcNode()` 一层层向下要行。所以"完成 SQL 执行过程"的入口是 `PortalRun()`。

### 1.3 关于执行计划图，哪些说法正确（多选）

执行计划（实测，与课件完全一致）：

```text
 Hash Join  (cost=270.00..587.49 rows=9999 width=12)
   Hash Cond: (s.id = r.id)
   ->  Seq Scan on s  (cost=0.00..180.00 rows=9999 width=12)
         Filter: (value > 100)
   ->  Hash  (cost=145.00..145.00 rows=10000 width=4)
         ->  Seq Scan on r  (cost=0.00..145.00 rows=10000 width=4)
```

**答案：A、C（考点：这两步都是"全表扫描"，不是索引扫描）**

判据只有一条：`Seq Scan` 就是顺序全表扫描，`Index Scan / Index Only Scan` 才是索引扫描。
两张表虽然有 `idx_r_id`、`idx_s_id` 索引，但这里都走了全表扫描——因为要取的行占全表比例太高，
走索引反而要回表随机读，CBO 算下来不划算。

> **两点必须说清楚的细节**（这两句话的后半段表述不严谨）：
>
> 1. 选项 A 说"读出表 s 的每一行，**然后构建 HASH 表**"——扫描 s 确实发生，但**HASH 表是用 r 建起来的**。
>    PG 的 Hash Join 里，`inner`（`righttree`，本例是 `Hash → Seq Scan on r`）建表，
>    `outer`（`lefttree`，本例是 `Seq Scan on s`）去探测。
> 2. 选项 C 说"读出表 r 的每一行，**然后到 HASH 表中搜索**"——读 r 建表是对的，
>    但"搜索"这一步不属于 `Hash` 节点，而属于 `Hash Join` 节点（对 s 的每一行去探测）。
>
> 所以若严格按"谁负责建表、谁负责探测"来判，A、C 的后半句都不准确；但按本题的考点
> （全表扫描 vs 索引扫描），A、C 是正确选项。

### 1.4 为什么要看"活"的代码（多选）

**答案：B、C、D**

- **A 错**："代码无所谓死活"是不成立的。静态阅读能看懂**控制流**，但看不到某个 `PlanState`
  在运行时的实际取值、某个 buffer 里到底是哪一版行、某个 `switch` 走了哪个分支。
- **B 对**：`gdb` 附加到运行中的 backend，`p *snapshot`、`p *htup` 能直接看到变量与内存里的真实数据，
  这是理解 MVCC、执行器状态机最有效的手段。
- **C 对**：`watch` 盯住某个地址（例如 `htup->t_infomask`），一被改写就停；
  `x/8x 0x...` 直接看内存十六进制。比"读代码猜"可靠得多。
- **D 对**：活代码与死代码是互补的——先读源码建立框架（知道该在哪下断点），
  再用 gdb 验证，再回头查资料确认设计意图。三者缺一不可。

### 1.5 图中的执行计划，正确的说法（多选）

**答案：B、C**

- **A 错**：说"一定是全表扫描 S 建 HASH 表，不会从 R 建"。建哪边由**优化器**根据代价决定，
  PG 还可能选 `Nested Loop`、`Merge Join`（`SET enable_hashjoin = off` 就能看到 Merge Join），
  不存在"一定"。
- **B 对**：选哪条路是优化器的活，它比较的是代价（CBO）。
- **C 对**：优化器产出执行计划，执行器按计划读写表——这正是"编译器 / 可执行文件"的类比。
- **D 错**：因为 A 错，所以"以上都正确"不成立。

### 1.6 看图选择正确的选项（多选）

**答案：A、B**

- **A 对**：`PortalRun()` 是执行器入口（同 1.2）。
- **B 对**：`ExecMergeJoin()` 是"排序合并连接"算子的实现函数，`ExecProcNode()` 通过函数指针
  `ExecProcNodeReal` 分发到它。
- **C 错**：Merge Join 有 `lefttree`、`righttree` 两棵子树，说明它一次只处理**两个输入**，
  但**不等于只能做两表 Join**。三表 `A JOIN B JOIN C` 会被拆成两层：下层 `A JOIN B` 的结果作为
  上层的左子树，再与 `C` 连接。树的每一层都是二元算子，多层叠加就实现了多表连接。
- **D 错**：多表连接不会报错，会生成一棵更深的计划树。

### 1.7 `ExecutorRun` 与 `standard_ExecutorRun` 的调用目的

**答案：B（为了提供 Hook 能力，与计划树执行无关）**

这是 PG 里典型的"钩子（hook）"写法：

```c
/* 简化示意 */
void ExecutorRun(QueryDesc *queryDesc, ...)
{
    if (ExecutorRun_hook)                 /* 开发者可注入自己的实现 */
        ExecutorRun_hook(queryDesc, ...);
    else
        standard_ExecutorRun(queryDesc, ...);
}
```

- `standard_ExecutorRun()` 才是真正干活的那个；
- `ExecutorRun()` 只是**外壳**，允许扩展（如 `pg_stat_statements`、审计、性能统计）在前后插入逻辑。

A 错在"这是计划树执行的要求"——计划树执行完全不依赖这层外壳；C 错在"它们是宏"——是真正的函数。

### 1.8 `ExecMergeJoin()` 对应图中哪一层的 `Next()`

**答案：B、C（中间层的 `left.Next()` 与 `right.Next()`）**

迭代器模型（ITERATOR MODEL）里，每个算子的 `Next()` 都长成"向孩子要一行、处理、返回"：

| 层 | 文本框内容 | 对应 |
| --- | --- | --- |
| 最上层 | `for t in child.Next(): emit(projection(t))` | 投影 π |
| 中间层 | `for t1 in left.Next(): ...` / `for t2 in right.Next(): ...` | 联接（Join） |
| 第三层 | `for t in child.Next(): if evalPred(t): emit(t)` | 选择 σ |
| 最下层 | `for t in R: emit(t)` / `for t in S: emit(t)` | 表扫描 |

`ExecMergeJoin()` 内部要**同时**从左右两棵子树取行（比较 `left` 和 `right` 的当前行，
小的那边前进），所以它对应的正是**中间层**的 `left.Next()` 和 `right.Next()` 这两个调用。

> 题目写的是"选择正确的选项"（单数），但 `ExecMergeJoin()` 确实会调用左右两侧的 `Next()`，
> B、C 两个选项描述的是同一层的两个调用，都对。若必须单选，说明题目本身不严谨。

### 1.9 `ExecutePlan()` 对应哪个文本框

**答案：A（最上层映射操作的文本框）**

`ExecutePlan()` 是**驱动整个计划树的最外层循环**：

```c
ExecutePlan(...)
{
    for (;;)
    {
        slot = ExecProcNode(planstate);   /* 相当于"取下一行"，即最外层的一次 Next() */
        if (TupIsNull(slot)) break;
        /* 把 slot 写进结果集 / 发给客户端 */
    }
}
```

它对应迭代器模型里"最外层那个 `for` + emit"的结构：**它自己不产生数据，只是反复向根节点要行并且输出**。
第二层的"两个 for"是 Join 算子自己的逻辑，第三层是 σ 的过滤逻辑，都不是 `ExecutePlan`。

### 1.10 `S.value > 100` 在哪个阶段执行

**答案：C（`ExecMergeJoin()` 中，进入左树后，在 `ExecScan()` 中执行过滤）**

关键在于**过滤条件下推（predicate pushdown）**：

```text
 Merge Join
   ->  Seq Scan on s          ← 左树：Filter: (value > 100) 在这里
   ->  Index Scan / Sort on r ← 右树
```

- 优化器把 `S.value > 100` 下推进了 s 的扫描节点；
- 执行时 `ExecMergeJoin()` 先向**左子树**要行，左子树的 `ExecScan()` 在
  `ExecScanFetch()` 拿到元组后立刻用 `qual` 求值，不满足的元组直接被丢弃，**不会上送到 Join**；
- 所以过滤发生在扫描层（左树），不是 Join 层，也不是最外层 `ExecutePlan()`。

A 错（Join 不做这个过滤）；B 错（`ExecutePlan()` 只负责取行和输出）；
D 错（过滤在左树 s 上，不在右树 r 上）。

## 二、问答分析题

### 2.1 简述执行计划的执行过程

以课件中的查询为例：

```sql
Select R.id, S.cdate FROM R JOIN S ON R.id = S.id WHERE S.value > 100;
```

#### （1）执行计划（实测）

```text
 Hash Join  (cost=270.00..587.49 rows=9999 width=12)
   Hash Cond: (s.id = r.id)
   ->  Seq Scan on s  (cost=0.00..180.00 rows=9999 width=12)
         Filter: (value > 100)
   ->  Hash  (cost=145.00..145.00 rows=10000 width=4)
         ->  Seq Scan on r  (cost=0.00..145.00 rows=10000 width=4)
```

加上 `ANALYZE` 看真实执行情况：

```text
 Hash Join (actual time=9.710..33.722 rows=10000 loops=1)
   Hash Cond: (s.id = r.id)
   Buffers: shared hit=100
   ->  Seq Scan on s (actual time=0.020..4.901 rows=10000 loops=1)
         Filter: (value > 100)
   ->  Hash (actual time=9.658..9.659 rows=10000 loops=1)
         Buckets: 16384  Batches: 1  Memory Usage: 480kB
         ->  Seq Scan on r (actual time=0.007..2.792 rows=10000 loops=1)
 Execution Time: 38.392 ms
```

这份输出里藏着执行过程的全部信息，逐条读：

| 观察 | 说明 |
| --- | --- |
| `Hash` 节点 `actual time=9.658..9.659`, `loops=1` | 建表只做一次，且**在 Join 开始出第一行之前就已经把 r 全读完**（9.658ms 启动，9.659ms 结束） |
| `Buckets: 16384, Batches: 1, Memory Usage: 480kB` | HASH 表完全在内存里，没有落盘分批（Batches=1） |
| `Seq Scan on s` 无 `loops=n` 嵌套 | 它是 Hash Join 的**外层（probe 侧）**，每取一行就探测一次 |
| `shared hit=100`（55 + 45） | r、s 各 45/55 个页，全在 shared buffer 里命中，没有物理读 |

#### （2）执行流程（自外向内 + 自内向外的"拉"模型）

```text
PortalRun()
 └─ ExecutorRun() / standard_ExecutorRun()
     └─ ExecutePlan()                     ← 最外层 for(;;)，反复要行
         └─ ExecProcNode()                ← 函数指针分发到根节点
             └─ ExecHashJoin()            ← 状态机，分两个阶段
                 ├─ 阶段 1: HJ_BUILD_HASHTABLE
                 │    ExecHashTableCreate() 建 16384 个桶
                 │    for (;;) 从 inner（righttree = Hash → Seq Scan on r）取行
                 │       计算 hash(r.id)，挂到对应桶的链上
                 │    取完 → hj_JoinState = HJ_NEED_NEW_OUTER
                 └─ 阶段 2: HJ_NEED_NEW_OUTER
                      slot = ExecProcNode(lefttree)   → Seq Scan on s
                              └─ ExecScan() 先用 qual 过滤 value > 100
                      if (TupIsNull(slot)) 结束
                      ExecScanHashBucket()  用 s.id 的 hash 值找到桶，逐条比对 r.id
                      命中 → 把 (s.cdate, r.id) 组装成结果元组返回
```

几个要点：

1. **"拉"（pull）而不是"推"（push）**：最上层 `ExecutePlan()` 调一次根节点的 `Next()`，
   根节点再调子节点的 `Next()`，一路拉到底层的表扫描；每一层只负责"给我下一行"。
   这就是**火山模型 / 迭代器模型**。
2. **两个阶段的分界点是状态机变量** `hj_JoinState`：先 `HJ_BUILD_HASHTABLE`（把 r 全部读进内存建表），
   再 `HJ_NEED_NEW_OUTER`（对 s 的每一行探测）。`EXPLAIN ANALYZE` 里 `Hash` 节点
   `actual time=9.658..9.659` 正是阶段 1 的耗时。
3. **过滤在扫描层完成**：`S.value > 100` 被下推到 `Seq Scan on s` 的 `Filter`，
   不满足的行在上送前就被丢掉，Join 只处理剩下的行。
4. **不物化中间结果（除了 HASH 表）**：r 的 10000 行没有整表缓存，只有 hash 表（480 KB）常驻；
   s 的行是流式取、流式探测、流式返回。
5. **结果逐行返回**：`ExecutePlan()` 每拿到一个非空 slot 就通过 `receiver`（DestReceiver）
   发给客户端，所以客户端是"边算边收"，不是等全部算完。
6. **什么时候停**：`ExecProcNode()` 返回 `NULL`（s 取完）时退出循环，`PortalRun()` 返回，
   执行器清理（释放 hash 表、快照、内存上下文）。

#### （3）为什么"读 s 建表"和"读 r 探测"会反过来

一个常见的困惑是：SQL 里写的是 `R JOIN S`，为什么 PG 拿 **r** 建表、拿 **s** 探测？

- `Hash Join` 把**行数少 / 结果集小**的一侧作为 build side（建表），另一侧作为 probe side；
- 这里 r、s 都是 10000 行，优化器按代价选了 r 作 inner（`Hash Cond: (s.id = r.id)`，
  注意等号左边是 s，说明 s 是 probe 侧）；
- 计划树里 `lefttree` = 外层 = probe 侧 = `Seq Scan on s`，`righttree` = 内层 = build 侧 = `Hash`。

这也正是 1.3 题里"A 的'扫描 s 后建 HASH 表'"不准确的原因：建表用的是 r，扫描 s 是在探测。

## 三、思考题：数据库与商业应用软件的演进关系，以及对 AI 系统未来的启示

### 3.1 数据库演进的三次"分层"

**（1）层次/网状模型：数据即指针**

课件里"学校 → 专业 → 班级 → 学生"的结构，本质是把**数据之间的关系写死在指针里**。
应用要拿一个学生的电话，得自己顺着"学校指针→专业指针→班级指针→学生指针"走。
访问路径是**程序员编写的**，所以语言是过程式的（DL/I 嵌在 COBOL 里）。
数据怎么存，程序就怎么写，两者强耦合。

**（2）关系模型：数据与访问路径解耦**

关系模型做了一件极简的事：把数据表示成**二维表**，把操作抽象成**关系代数**
（选择、投影、连接、并交差），把"怎么走"交给**运算规律**（选择下推、谓词传递……）。

课件里特别强调了一句容易被忽略的话：

> 关系模型胜出的主要原因，不是存储方式的简单改变，而是关系代数，以及基于关系代数的声明式语言。

也就是说，**胜出的关键是"抽象 + 等价变换规则"，不是"二维表"这种存储形式**。
一旦有了等价变换规则，SQL 就可以被改写（例如把 `a.cid=2026001` 也加到 b 上），
执行顺序可以和用户写的完全不同，但语义不变——这才是数据库能做优化器的前提。

**（3）现在：一个内核，多种形态**

关系模型这一层抽象之后，存储与执行可以自由替换：BTree/LSMTree、行存/列存、
单机/分布式、HASH Join/Merge Join。课件 1.2 的选项 D 说的正是这一点：
"LSMTree 是新型存储结构，用了 LSMTree 的仍然是关系型数据库"。
**抽象稳定，实现可以一直换。**

### 3.2 数据库与商业应用软件的"分层"关系

课件把这条因果链讲得很清楚：

1. 数据建模完成、数据接入数据库之后，**应用开发只需要关注业务逻辑**，
   不必关心 CPU、内存、存储的原理、调优、排故；
2. 之所以能做到这一点，是因为 SQL 是**声明式**的：应用只提"要什么"，不提"怎么拿"；
3. 于是数据库和商业应用被切成**两层**：下面一层保证 ACID、并发、恢复、性能，
   上面一层只写业务规则。过程式语言时代做不到这一点——那时应用得自己实现访问路径。

这就是 ERP、财务这类 OLTP 系统能大规模工程化的根本原因：**分层让复杂度被"关"在了下层**。
反过来，一旦下层的能力边界（比如一致性、性能）被突破，上层应用形态就会跟着变——
这也是为什么课件说"OLTP 发展趋缓，OLAP 还在发展中"。

### 3.3 对 AI 系统未来发展的启示

我把上面这条"演进逻辑"抽象成四句话，逐条对应到 AI 系统：

#### 启示一：赢的往往不是"更聪明的实现"，而是"更好的抽象层"

关系模型赢，不是因为二维表比指针"更好存"，而是因为它给出了**一套可等价变换的抽象**。
今天的 AI 系统同样处在"层次/网状模型"阶段：每个团队自己写数据管道、自己拼 RAG、
自己调 prompt 链路，**数据和流程是强耦合的**——很像当年"访问路径写死在程序里"。

可以预期，AI 系统也会出现自己的"关系模型时刻"：
把"模型能力"和"数据/流程"用一层稳定的抽象隔开，
让上层只描述"意图"，下层自己决定"怎么执行"。

#### 启示二：声明式 + 优化器 = 把"怎么做"交给系统

SQL 是声明式的，所以数据库可以在**不改语义**的前提下任意改写执行方式。
大模型的 prompt 也是"声明式"的（描述想要什么），但目前缺一个"优化器"：
谁来把 prompt 改写成更便宜、更可靠的执行计划？谁来估算"这个改写的代价"？

现在有两条路已经在往这个方向走：
- **推理时的搜索/规划**（test-time compute、agent 的 plan-and-execute），
  相当于在执行期做"基于代价的选择"；
- **编译式的优化**（把 prompt/流程编译成更高效的中间表示），
  相当于 RBO/CBO。

#### 启示三：等价变换的"规则库"才是核心资产

关系代数的灵魂是"保证等价的运算规律"。数据库的优化器之所以敢乱改执行顺序，
是因为每一次改写都有**可证明的等价性**。

AI 系统最缺的恰恰是这个：现在很多"优化"（换模型、加 RAG、改 prompt）
是**靠评估指标试出来的**，不是靠等价性证明出来的。
所以指标一抖，就不知道是"优化生效了"还是"碰巧"。
要走向工程化，需要建立**可验证的等价性/一致性判据**，哪怕只在受限场景内成立
（就像数据库只在关系代数允许的范围内改写）。

#### 启示四：分层里的"缓存/日志"思想会重现

数据库的很多机制本质上是在"用空间和顺序换延迟"：
shared buffer 缓存热页、WAL 把随机写变顺序写、MVCC 让读写不互相阻塞。

AI 系统里已经有同构的东西：
- **KV Cache** ≈ shared buffer（省掉重复计算）；
- **RAG / 向量库** ≈ 二级存储（把"模型外"的知识按需取回）；
- **checkpoint / 重放** ≈ WAL（让长任务可以中断恢复）。

课件里有一个判断：**"模型之内是主要数据，模型之外只是辅助"**。
类比到数据库：shared buffer 是主要的，RAG 相当于外存——外存再大也不能替代缓存策略。
所以 AI 系统未来的竞争力，很可能不在"外挂了多少知识"，而在"内部的调度与缓存做得多好"。

#### 启示五（反过来的）：不要被"当前实现"绑住

关系模型能活五十年，是因为它把"数据表示 + 运算 + 运算规律"抽象出来了，
**没有把任何硬件特性写进这个抽象**（BTree、LSMTree、列存都能装进来）。

对 AI 的启示是：设计系统时不要把"当前这一代模型的特性"（上下文长度、注意力机制、
某种 tokenizer）当成永恒前提。今天围绕 128K 上下文做的所有工程，
可能明年就因为架构变化而作废。**该抽象的是"意图—执行—验证"这条链路，不是某个模型的参数。**

### 3.4 小结

数据库的演进给出的最重要一条经验是：

> **把"要什么"和"怎么做"分开，用可证明等价的变换规则撑起中间那一层。**

关系模型靠这一条吃掉了层次/网状模型，也把商业应用从"自己管数据"里解放出来。
今天的 AI 系统正处在"过程式"阶段——能力很强，但流程与实现强耦合、缺少等价变换规则、
缺少可验证的一致性与代价模型。谁能先把这一层抽象做出来，谁就相当于做出了 AI 时代的"关系模型"。
