## 二、选择题

### 1.1 以下正确的是（多选）

**答案：A、C**

- **A 对**：关系型数据库最大的特点是使用了**声明式语言**，"是不是 SQL"确实无所谓。
  SQL 只是关系代数最成功的载体；只要满足"声明式 + 关系代数"这一层抽象，用别的语法也是关系型。
- **B 错**：把"用了 SQL"当成最大特点，是把载体当成了本质。
- **C 对**：层次/网状模型使用过程式语言——例如 DL/I 并不是一门独立语言，
  而是嵌在 COBOL/PL/I 里的**函数调用接口**，程序员必须写出访问路径。
- **D 错**：关系型数据库**支持**过程式语言，只是"核心 DML 是声明式的"。
  PostgreSQL 有 PL/pgSQL、存储过程、游标，MySQL 有存储过程——它们是在声明式内核之上的过程式扩展。

### 1.2 以下正确的是

**答案：D（以上都不对）**

- **A 错**："只有用了 BTree、SQL 的才是关系型数据库"——存储结构（BTree）和语法（SQL）都不是判定标准，
  列存、LSMTree、图存都可以承载关系模型。反例：SQLite 用 BTree 但关系模型很完整；
  而一个用 BTree 存键值的 KV 引擎并不是关系型数据库。
- **B 错**：LSMTree 只是存储结构，与"是不是关系型"无关。openHalo/PostgreSQL 也支持可插拔的表访问方法。
- **C 错**：关系模型当然支持分布式——分片、复制、分布式事务都是关系模型之上的工程实现；
  LSMTree 也不是"专为分布式而生"（它首先是为顺序写优化）。

### 1.3 关于执行计划，正确的是

**答案：D（以上都正确）**

- **A**：执行计划相当于数据库的"可执行文件"——优化器相当于编译器，计划就是编译产物；
- **B**：执行计划里确实包含访问路径（全表扫描、索引扫描）和连接方式（Nested Loop、Merge Join、Hash Join）；
- **C**：这些访问路径/连接方式相当于数据库的"汇编指令"，由计划树把它们组织起来。

三句都对，故选 D。

### 1.4 执行计划的正确执行顺序

图：

```text
 Hash Join
   Hash Cond: (s.id = r.id)
   ->  Seq Scan on s
   ->  Hash
         ->  Seq Scan on r
```

选项：(a) 读取表 S 一行　(b) 读取表 R 所有行，在内存中创建 HASH 表　(c) 在 HASH 表中搜索

**答案：B（b → a → c）**

- 先 **b**：`Hash` 节点把 **r** 的全部行读进来，按 `r.id` 建 HASH 表（这一步必须做完，否则没得探测）；
- 再 **a**：从 **s** 取一行：
- 再 **c**：用 `s.id` 的 hash 值定位桶，在桶里比对 `r.id`，命中就输出。

然后对 s 的下一行重复 a、c，直到 s 取完。

**为什么 C（缺关键步骤）不对**：看图能看出 `Hash` 节点下面还挂着 `Seq Scan on r`，
"读 r 建表"这个步骤在计划里是明确的，不缺。

> 一个细节：这里"建 HASH 表"的是 **r**，"探测"的是 **s**。
> `Hash Join` 总是拿 `inner`（righttree，本例是 `Hash`）建表，拿 `outer`（lefttree，本例是 `Seq Scan on s`）探测。

### 1.5 `((PLAN *)hjPlan)->type` 的用法是否正确

```c
typedef struct Plan { Node type; /* ... */ } PLAN;
typedef struct PlanHashJoin {
    PLAN bplan;                        /* 第一个成员！ */
    char nameLeft[TABLE_NAME_MAX];
    char nameRight[TABLE_NAME_MAX];
    /* ... */
} PLANHashJoin;
```

**答案：C（灰色下划线的用法是正确的，也可以 `hjPlan->bplan.type`）**

两个关键点：

1. **C 结构体里，第一个成员的地址 == 结构体本身的地址**。这是 C 标准保证的
   （`PLANHashJoin *` 与 `PLAN *` 之间可以安全互转的前提）。
   所以 `((PLAN *)hjPlan)->type` 和 `hjPlan->bplan.type` 访问的是**同一块内存的同一个字段**。
2. `hjPlan->bplan->type` 是**错的**：`bplan` 是结构体对象而不是指针，
   对非指针用 `->` 编译器会直接报错（`invalid type argument of '->'`）。

这就是 PG 里"用第一个字段实现继承"的手法：`Plan` 是基类，`PlanHashJoin` 是派生类，
统一的 `Node *` 可以在计划树里被自由转换，靠的就是"首成员地址相同"。
课件里说 Plan 的数据结构"像洋葱一样，一层包一层"，指的就是这个。

### 1.6 图右的左树、右树分别对应图左哪些表（多选）

**答案：C（无法确定，可结合数据库中的执行计划和 plan tree 才能确定）**

理由：**逻辑树和物理树的左右可以不一致**。

- 图左是 SQL 的**逻辑结构**：`R JOIN S`，习惯上把 R 画在左、S 画在右；
- 图右是**执行计划树**：左右由优化器决定。本例的实测计划是

  ```text
   Hash Join
     ->  Seq Scan on s     ← lefttree（outer，探测侧）
     ->  Hash
           ->  Seq Scan on r   ← righttree（inner，建表侧）
  ```

  也就是说 **lefttree 是 s，righttree 是 r**，与"左=R、右=S"的直觉**正好相反**。

所以 A、B 都不成立（它们是同一个说法，题面里 A、B 文字重复，应是排版问题）。
D 说"结合 Portal 结构才能确定"也不对：`Portal` 只是执行期的句柄，
表与左右树的对应关系在**计划树（PlanState 树）**里就已经定死了，不需要看 Portal。

> 推论：`ExecHashJoin` 的 `lefttree`/`righttree` 只是"计划树的两个分支"，
> **不要**从 SQL 的书写顺序去推断谁是左树。

## 三、问答分析题

### 2.1 为什么说 SQL 是声明式语言

**一句话：SQL 描述的是"结果必须满足什么性质"，而不是"用哪条路径把结果算出来"。**

可以从四个层面看：

#### （1）语义层面：SQL 的操作对象是"集合"

```sql
Select R.id, S.cdate FROM R JOIN S ON R.id = S.id WHERE S.value > 100;
```

这句话说的是："存在一个结果集合，它由 R、S 中满足 `R.id = S.id` 且 `S.value > 100` 的行组成，
每行取 `R.id`、`S.cdate` 两列"。

- 它**没有**说先扫哪张表、用不用索引、用哪种连接算法、循环谁在外层；
- 关系代数里，`σ`（选择）、`π`（投影）、"连接"都是**集合运算**，
  运算结果与"计算顺序"无关——这正是"声明式"的数学基础。

#### （2）执行层面：同一句 SQL 有无数种执行方式

我实测过同一条 SQL 在同一个库里的不同计划：

```sql
-- 默认
explain Select R.id, S.cdate FROM R JOIN S ON R.id = S.id WHERE S.value > 100;
 Hash Join  (cost=270.00..587.49 rows=9999 width=12)
   Hash Cond: (s.id = r.id)
   ->  Seq Scan on s ...
   ->  Hash -> Seq Scan on r ...

-- 关掉 hashjoin
set enable_hashjoin = off;
 Merge Join  ...（同样的结果集，完全不同的执行方式）
```

用户一行 SQL 没改，执行路径却可以完全不同，**结果集却完全一样**。
这就是声明式语言的核心特征：**语义与执行计划解耦**。

#### （3）优化层面：可以"等价改写"

正因为有"保证等价的运算规律"（选择下推、谓词传递、连接顺序交换……），
优化器才敢改写。课件给的例子非常典型：

```sql
-- 原始
select * from class a, stu b where a.cid=b.cid and b.name='张三' and a.cid=2026001;
-- 优化器可以等价地补上（谓词传递）
select * from class a, stu b where a.cid=b.cid and b.name='张三' and a.cid=2026001 and b.cid=2026001;
```

改写后能先把 `b` 过滤到很小，再去连接。**如果 SQL 是过程式的（写死了访问路径），这种改写就不合法**。

#### （4）对比层面：过程式语言长什么样

层次/网状模型的 DL/I 是过程式的：

```text
GU  CLASS    （取班级）
GN  STUDENT  （顺着指针取下一个学生）
...
```

程序员必须知道"学校→专业→班级→学生"的指针链怎么走，**访问路径写在程序里**。
换了存储布局或加了索引，程序就得改。SQL 不需要——它只说"我要什么"。

#### 边界说明

SQL 也不是"纯"声明式的：
- `ORDER BY` 暗示了顺序，`LIMIT` 依赖顺序；
- 游标（`DECLARE CURSOR`）、`FOR UPDATE`、`PL/pgSQL` 都是过程式成分；
- 但**核心的 DML**（SELECT/INSERT/UPDATE/DELETE）是声明式的，这一点决定了整个体系的性质。

### 2.2 层次/网状模型数据库与关系型数据库最本质的区别

**一句话：最本质的区别不是"二维表 vs 指针"，而是"数据与访问路径是否解耦"——
关系模型多出了"关系代数 + 等价变换规则"这一层抽象。**

分三层展开：

#### （1）数据表示层：指针网络 vs 二维表

| | 层次/网状模型 | 关系模型 |
| --- | --- | --- |
| 数据的组织 | 记录 + 记录之间的**指针**（父子、系） | 表 + 行 + 列，行之间**没有指针** |
| 关系怎么表达 | 用指针"物理地"连起来 | 用**值**相等来表达（外键、连接条件） |
| 导航方式 | 顺着指针走（导航式） | 声明连接条件，由系统算 |

这一层的差别很直观，但**不是最本质的**——因为二维表本身也可以实现成指针（很多存储引擎内部就是）。

#### （2）语言层：过程式 vs 声明式

- 层次/网状的 DL/I：`GU/GN/GNP` 这些调用就是"走哪条指针"的指令，**路径由人指定**；
- 关系模型：`SELECT ... WHERE ...`，**路径由优化器决定**。

#### （3）本质层：有没有"可等价变换的抽象"

这是我认为最关键的一层。关系模型真正的杀手锏是：

> **关系代数 + 一组保证等价的运算规律 → 使自动优化成为可能。**

- 因为 `σ` 可以下推、连接可以交换顺序，所以优化器能"任意改执行方式而语义不变"；
- 因为语义不变，应用层才敢完全不关心执行；
- 因为应用层不关心执行，数据与程序才能**真正解耦**（逻辑数据独立性 + 物理数据独立性）。

层次/网状模型没有这层抽象，所以它的"优化"只能在很局部做，
程序与数据的耦合无法解除——**这才是它被淘汰的根本原因**。

课件里那句"关系模型胜出的主要原因，不是存储方式的简单改变，而是关系代数以及基于关系代数的
声明式语言"，说的就是这个意思。

> 一个佐证：现代图数据库（网状模型的"变形"）之所以能重新流行，恰恰是因为它
> **补上了这一层**——节点、边、属性、关系都有了，再总结出点/边上的运算与运算规律，
> 应用层就能"只提需求、不关心实现细节"。这说明"网状"不是原罪，"缺少等价变换抽象"才是。

### 2.3 如何找到表对应的文件（实测）

按题目给的建表语句，我一步步把文件找出来并解析了页结构。

#### 步骤 1：建表插数

```sql
create table vage (id1 int, c1 varchar(30), id2 int, c2 varchar(30));
insert into vage

       'AAAAAAAA'||generate_series(1,5),
       generate_series(1,5)+100,
       'aaaaaaaa'||generate_series(1,5);

select * from vage;

-----+-----------+-----+-----------
   1 | AAAAAAAA1 | 101 | aaaaaaaa1
   2 | AAAAAAAA2 | 102 | aaaaaaaa2
   3 | AAAAAAAA3 | 103 | aaaaaaaa3
   4 | AAAAAAAA4 | 104 | aaaaaaaa4
   5 | AAAAAAAA5 | 105 | aaaaaaaa5
```

#### 步骤 2：从系统表拿到"物理标识"

```sql
select oid, relname, relfilenode, reltablespace, relpages from pg_class where relname='vage';
  oid  | relname | relfilenode | reltablespace | relpages
-------+---------+-------------+---------------+----------
 20829 | vage    |       20829 |             0 |        0

select oid as database_oid, datname from pg_database where datname=current_database();
 database_oid |  datname
--------------+-----------
        14254 | halo0root
```

三个关键字段：

| 字段 | 含义 |
| --- | --- |
| `pg_class.oid` | 表在**系统目录**里的对象号（逻辑标识） |
| `pg_class.relfilenode` | 表对应的**物理文件号**（通常等于 oid，但 `VACUUM FULL`、`REINDEX`、`TRUNCATE` 会换新文件号） |
| `pg_database.oid` | 数据库标识，对应 `base/` 下的子目录名 |

#### 步骤 3：拼出文件路径

PG 的目录约定是：

```text
$PGDATA/base/<数据库 oid>/<表 relfilenode>
```

一条 SQL 就能算出来，不用手工拼：

```sql
select pg_relation_filepath('vage') as filepath, pg_relation_size('vage') as bytes;
     filepath     | bytes
------------------+-------
 base/14254/20829 |  8192
```

所以文件就是：

```text
openhalo-14.18/data/base/14254/20829
```

补充（作业题外的常见追问）：

| 情况 | 路径规则 |
| --- | --- |
| 普通表 | `base/<dboid>/<relfilenode>` |
| 超过 1 GB | 按 1 GB 分段：`<relfilenode>.1`、`<relfilenode>.2` … |
| 指定了表空间 | `pg_tblspc/<spcoid>/PG_<version>_<dboid>/<relfilenode>` |
| 索引 | 同样规则，`relfilenode` 取索引自己的 |
| 临时表 | `base/pgsql_tmp/...` 或 `base/<dboid>/t<backendid>_<relfilenode>` |

#### 步骤 6：逐字段解析（自己写了个解析脚本）

我写了一个 `parse_page.py` 按 `bufpage.h` / `htup.h` 的定义解析这 8192 字节：

```text
--- PageHeaderData (24 字节) ---
  0x00 pd_lsn               = 0/20543C0  (8 字节)
  0x08 pd_checksum          = 0
  0x0A pd_flags             = 0
  0x0C pd_lower             = 44          ← 行指针区末尾（5 个指针，24 + 5*4 = 44）
  0x0E pd_upper             = 7912        ← 元组区起点（从页尾向上长）
  0x10 pd_special           = 8192
  0x12 pd_pagesize_version  = 0x2004      ← 页大小 8192 + layout version 4
  0x14 pd_prune_xid         = 0
  => 空闲空间 (pd_upper - pd_lower) = 7868 字节

--- ItemIdData 行指针区：5 个 × 4 字节 (0x18 ~ 0x2C) ---
  lp | 文件偏移 | lp_off | lp_flags | lp_len
   1 |   0x1FC8  |   8136 |    1     |  54
   2 |   0x1F90  |   8080 |    1     |  54
   3 |   0x1F58  |   8024 |    1     |  54
   4 |   0x1F20  |   7968 |    1     |  54
   5 |   0x1EE8  |   7912 |    1     |  54

--- 元组 1（lp_off = 0x1FC8）---
    t_xmin=755 t_xmax=0 t_field3=0 t_ctid=(0,1)
    t_infomask2=0x0004 (属性数 4)  t_infomask=0x0902  t_hoff=24
    属性数据 (30 字节): 010000001541414141414141413100006500000015616161616161616131
    属性1 int4   @+ 0: 01000000  = 1
    属性2 varchar@+ 4: 头部 15 → 变长总长 10 字节，内容 'AAAAAAAA1'
    (对齐填充 2 字节: 0000)
    属性3 int4   @+16: 65000000  = 101
    属性4 varchar@+20: 头部 15 → 变长总长 10 字节，内容 'aaaaaaaa1'
```

这些数字都能对上，验算如下：

**（1）页头 24 字节**

| 偏移 | 字段 | 含义 |
| --- | --- | --- |
| 0x00 | `pd_lsn` (8) | 最后修改本页的 WAL 位置 |
| 0x08 | `pd_checksum` (2) | 页校验和（本机未开） |
| 0x0A | `pd_flags` (2) | 页标志位 |
| 0x0C | `pd_lower` (2) | 低水位：行指针区末尾，**向上长** |
| 0x0E | `pd_upper` (2) | 高水位：元组区起点，**向下长** |
| 0x10 | `pd_special` (2) | 页尾特殊区（堆表里等于页大小） |
| 0x12 | `pd_pagesize_version` (2) | `0x2004` = 8192 + 版本 4 |
| 0x14 | `pd_prune_xid` (4) | 可清理的最老 xid 提示 |

**页内空间是从两头相向分配的**：行指针从 `pd_lower` 往上长，元组数据从 `pd_upper` 往下长，
中间 `[pd_lower, pd_upper)` 是空闲区。本例空闲 7868 字节。

**（2）行指针 4 字节**

一个 `ItemIdData` 用 32 位塞了三样东西：

```text
lp_off   : 15 bit   元组在页内的偏移（单位字节）
lp_flags :  2 bit   状态：0=未使用 1=正常 2=HOT重定向 3=已死
lp_len   : 15 bit   元组总长度（字节）
```

验算 lp 1：`0x006c9fc8` → `lp_off = 0x1FC8 = 8136`，`lp_len = 54`，`lp_flags = 1`。
5 个指针 × 4 字节 = 20 字节，加上 24 字节页头正好 `pd_lower = 44`。

**（3）元组头 23 字节 + 对齐**

| 偏移 | 字段 | 本例值 | 说明 |
| --- | --- | --- | --- |
| +0 | `t_xmin` (4) | 755 | 插入这行的事务号 |
| +4 | `t_xmax` (4) | 0 | 删除/更新这行的事务号，0 表示还活着 |
| +8 | `t_field3` (4) | 0 | 命令号 CID |
| +12 | `t_ctid` (6) | (0,1) | 指向自己（或更新后的新版本） |
| +18 | `t_infomask2` (2) | 0x0004 | 低 11 位是属性个数 = 4 |
| +20 | `t_infomask` (2) | 0x0902 | 标志位：`HEAP_XMAX_INVALID(0x800)` + `HEAP_XMIN_COMMITTED(0x100)` + `HEAP_HASVARWIDTH(0x2)` |
| +22 | `t_hoff` (1) | 24 | 从元组开头到属性数据的偏移 |

`t_hoff = 24` 而不是 23，是因为属性数据要从 **MAXALIGN（8 字节）** 边界开始，补了 1 字节。

**（4）属性数据 30 字节怎么来的**

```
id1  int4       4 字节
c1   varchar   10 字节（1 字节变长头 + 9 字符 'AAAAAAAA1'）
     对齐填充   2 字节（把下一个 int4 对齐到 4 字节边界）
id2  int4       4 字节
c2   varchar   10 字节（1 字节变长头 + 9 字符 'aaaaaaaa1'）
--------------
合计           30 字节
```

于是元组长度 = 24（头）+ 30（数据）= 54，正好等于 `lp_len`。

**（5）短变长头 `0x15` 是什么**

```text
0x15 = 0b0001_0101
  bit0 = 1        → 表示这是"1 字节变长头"
  其余位 0x15>>1 = 10 → 变长字段总长 10 字节（1 头 + 9 数据）
```

如果是超过 126 字节的长字符串，就会退化成 4 字节头；再大就会 TOAST 到 `pg_toast` 表里。

**（6）为什么磁盘上元组是"倒着排"的**

`lp 1` 在 0x1FC8、`lp 5` 在 0x1EE8 —— **插入越早的行，偏移越大（越靠近页尾）**。
因为元组区是从 `pd_upper` 开始**向下**分配的：新行从高地址往低地址长，行指针从低地址往高地址长。

#### 另一种更简单的找法

不用 `hexdump` 也能看，`pageinspect` 扩展直接给你解析好的视图：

```sql
create extension if not exists pageinspect;

select * from page_header(get_raw_page('vage', 0));
select lp, lp_off, t_xmin, t_xmax, t_ctid, t_infomask, t_data
  from heap_page_items(get_raw_page('vage', 0));
```

但**手算一遍 hexdump 是值得的**——只有自己按字节对过，才会真正记住
"页头 24 字节 / 行指针 4 字节 / 元组头 23+1 字节 / 短变长头 1 字节"这些常量。

| 项目 | 结果 |
