## 一、选择题

### 1.1 关于存储引擎，正确的有（多选）

数据库代码可分为网络接口、SQL 解析、优化器、执行引擎、事务引擎、WAL 日志体系、存储引擎 7 大部分。

**答案：B、D**

- **B 对**：存储引擎的主要作用是"为数据库**管理存储空间**与 I/O"。注意这里是"空间"，不是"文件"——
  数据库看到的是一堆 8 KB 的页、若干 segment、若干 fork，而不是路径和文件名。
- **D 对**：存储引擎**可以建立在操作系统的文件系统之上**（PG 默认的 `md` 就是走 `open/pread/pwrite`），
  也**可以绕过文件系统**直接管理块设备（这时 `smgr` 换成另一套实现即可，接口层完全不用改）。
- **A 不选**："管理文件与 I/O"这个说法把存储引擎等同于文件系统了。文件是**文件系统**的概念；
  存储引擎关心的是"第几个块的哪个偏移"，是不是"文件"由下层决定。
- **C 错**：存储引擎与文件系统不是"二选一"的冲突关系，而是**分层**关系（见 D）。

### 1.2 选择正确的（多选）

**答案：A、B、C、D（全选）**

| 选项 | 判断 | 说明 |
| --- | --- | --- |
| A | 对 | 文件系统相当于操作系统的"存储引擎"——它管理空间、提供 I/O 接口；数据库存储引擎既可以复用文件系统，也可以直接对块设备做空间管理 |
| B | 对 | 存储引擎的核心工作就是"空间元数据的管理 + 元数据检索"：哪些块属于哪个表、哪个块是空闲的、某表的第 N 页在哪个设备的哪个偏移 |
| C | 对 | 文件系统的 FAT、inode 表、extent 树，功能上正对应存储引擎的元数据（记录"哪块空间归谁"） |
| D | 对 | 元数据本身可能不大，但每次 I/O 都要查一次，**检索效率**直接决定 I/O 性能，这是存储引擎最难的地方之一 |

### 1.3 关于元数据的快速检索，正确的有（多选）

**答案：B、D**

- **A 错**："存储引擎自身元数据不会十分庞大，用遍历最高效"——恰恰相反。
  一次 I/O 就要查一次元数据，遍历的 O(N) 会直接变成 I/O 延迟；而且元数据量随表数/文件数增长，
  并不"不庞大"。所以必须用 HASH/BTree 之类做 O(1)/O(log N) 检索。
- **B 对**：目前主流的快速检索结构就是 HASH、BTree、SkipList、红黑树这几类，各自适用不同场景
  （HASH 适合精确匹配，BTree 适合范围与有序扫描，SkipList 适合并发插入的有序结构）。
- **C 错**："主流文件系统的元数据**都**使用 HASH"不成立。ext4 用 extent tree（B 树变体）+
  H-tree（目录哈希），NTFS 用 B+ 树，ZFS 用 object set + B 树。HASH 只是目录检索常用的一种。
- **D 对**：BTree 的一个重要特点是**页在缓存中和在存储设备上的格式一致**（都是定长页、都按块号组织），
  所以可以"原地读、原地改、原地写"，不需要序列化/反序列化。这也是 PG 的 BTree 索引能直接映射到
  8 KB buffer 页上的原因。

### 1.4 `smgr_open` 接口函数的正确声明

课件给的是 `f_smgr` 函数指针表。源码（`src/backend/storage/smgr/smgr.c`）里逐行核对：

```c
typedef struct f_smgr
{
    void      (*smgr_init) (void);                      /* may be NULL */
    void      (*smgr_shutdown) (void);                  /* may be NULL */
    void      (*smgr_open) (SMgrRelation reln);         /* ← 本题 */
    void      (*smgr_close) (SMgrRelation reln, ForkNumber forknum);
    void      (*smgr_create) (SMgrRelation reln, ForkNumber forknum, bool isRedo);
    bool      (*smgr_exists) (SMgrRelation reln, ForkNumber forknum);
    void      (*smgr_unlink) (RelFileNodeBackend rnode, ForkNumber forknum, bool isRedo);
    void      (*smgr_extend) (SMgrRelation reln, ForkNumber forknum,
                              BlockNumber blocknum, char *buffer, bool skipFsync);
    ...
} f_smgr;
```

**答案：D（`void open_reln(SMgrRelation reln)`）**

判据有三条：

1. **返回值是 `void`**：函数指针类型是 `void (*)(...)`，排除 A、B（返回值是 `SMgrRelation`）；
2. **参数按值传递** `SMgrRelation reln`，不是 `SMgrRelation *reln`，排除 C；
3. 另外，`SMgrRelation` 本身就是指针（`typedef SMgrRelationData *SMgrRelation;`），
   所以传值传的就是指针，不需要再套一层 `*`。

**为什么"打开"不返回句柄？** 因为句柄（`SMgrRelation`）在 `smgropen()` 里就已经拿到并缓存了：

```c
SMgrRelation
smgropen(RelFileNode rnode, BackendId backend)
{
    ...
    /* 先查 HTAB，没有就创建一个 SMgrRelationData 挂进去 */
    ...
    if (!reln->smgr_targblock) ...
    smgrsw[reln->smgr_which].smgr_open(reln);   /* 真正打开文件的是这一步 */
    return reln;
}
```

`smgr_open` 的职责是"把这个 SMgrRelation 的物理文件真正打开（建立 vfd）"，
句柄本身早已存在，所以返回 `void`。

```c
static const f_smgr smgrsw[] = {
    /* magnetic disk */
    {
        .smgr_init    = mdinit,
        .smgr_shutdown= NULL,
        .smgr_open    = mdopen,      /* ← 默认存储引擎把 smgr_open 实现为 mdopen */
        .smgr_close   = mdclose,
        .smgr_create  = mdcreate,
        ...
    }
};
```

### 1.5 关于"文件号"，正确的有（多选）

**答案：A、C、D**

- **A 对**：在操作系统里 `open()` 返回的是**文件描述符（fd）**，它本质上是进程 fd 表的下标。
  内核凭这个下标找到 `struct file`（含当前读写位置 `f_pos`、flags、指向 inode 的指针），
  再凭 inode 找到"文件在哪、多大、属于哪个设备"这些**元数据**。
- **B 错**：文件号**拿不到路径和文件名**。`fd` 指向 inode，而 inode 里没有路径字符串
  （路径是目录项里的名字，一个 inode 可以有多个硬链接、多个路径）。想从 fd 反查路径，
  Linux 上得读 `/proc/self/fd/N`，那不是文件号本身的能力。
- **C 对**：PG 的 `Vfd` 结构里确实存了 OS 文件号：

  ```c
  typedef struct vfd
  {
      int             fd;          /* current FD, or VFD_CLOSED if none  ← 就是它 */
      unsigned short  fdstate;
      ResourceOwner   resowner;
      File            nextFree;
      File            lruMoreRecently;
      File            lruLessRecently;
      off_t           fileSize;
      char           *fileName;    /* 文件路径（PG 自己记的） */
      int             fileFlags;
      mode_t          fileMode;
  } Vfd;
  ```

- **D 对**：`Vfd` 就是 PG 在文件系统之上又加的一层"虚拟文件描述符"层，原因很现实：
  - 每个 backend 进程能开的 fd 有上限（`ulimit -n`），而 PG 要同时打开很多表文件；
  - 于是 PG 只保留少量真实 fd，其余 VFD 关掉（`VFD_CLOSED`），按 LRU 复用；
  - 这样"打开 1000 张表"不需要 1000 个 fd。

### 1.6 关于 PMC，正确的有（多选）

**答案：B、D**

- **A 错**："Intel CPU 专有"不成立。AMD（`PERF_TYPE_RAW` + 各代 PMU）、ARM（PMUv3）、
  POWER、RISC-V 都有性能监控单元，Linux 用 `perf` 统一抽象。
- **B 对**：现代通用处理器基本都具备 PMU（Performance Monitoring Unit），
  这已经是标配而不是某个厂商的特性。
- **C 错**："只能统计指令数和周期"错得比较明显。PMC 能统计的事件很多：
  cache 访问/缺失（各级）、分支预测失败、TLB 缺失、总线周期、内存带宽、甚至某些微架构内部事件。
  本课程 0924 的作业就用到了 7 个事件。
- **D 对**：PMC 的**硬件**是独立的，但"可编程地访问它"依赖操作系统提供接口——
  Linux 上是 `perf_event_open(2)`，Windows 上是 ETW/`PERF_*` 相关接口。
  更要紧的是权限：`kernel.perf_event_paranoid` 决定了你能开哪些事件。

### 1.7 关于 PMC 计数器数量

**答案：C（取决于有多少记录计数结果的寄存器）**

PMU 里"可编程的事件选择器"可以很多（几十到几百个），但**真正能同时计数并保存结果的是寄存器**，
而寄存器只有十几个。所以"能同时打开多少个计数器"取决于**结果寄存器**的数量，不是内存大小（A 错），
也不是事件选择器的数量（B 错）。

### 1.8 为什么 PMC 寄存器只有 10 个左右

**答案：C（A、B 都有）**

- **A 的理由**：读 PMC 寄存器要走访存/系统调用，寄存器越多，每次采样要搬运的数据越多，
  会污染 Cache、占用内存带宽，**干扰被观测程序**——观测本身成了噪声源。
- **B 的理由**：硅片面积寸土寸金，可观测性硬件不是"计算"，没必要堆太多。
- **C** 把两条理由都包含了，所以选 C。

这也解释了一个工程上的取舍：**观测能力要给，但不能给到影响主业务的程度**。所以现代 PMU 的做法是
"少量寄存器 + 分时复用（multiplexing）"——多个事件轮流上机，用 `time_enabled/time_running` 折算。
（这一点在 0924 作业的 `pmc.c` 里已经处理过。）

## 二、问答分析题

### 2.1 为什么 PMC 类功能会成为现代处理器（CPU）的标配

**结论**：因为现代 CPU 的性能已经**无法靠软件"数指令"来推断**，必须由硬件提供"事实来源"（ground truth）。
PMC 就是硬件向软件开放的那扇观测窗口，成本极低、收益极大，所以成了标配。

#### 原因一：微架构太复杂，软件算不出真实代价

几十年前，一条指令大约一个周期，"数指令"就能估性能。现在一条 `ldr` 背后可能是：

```text
L1 命中      → 4 个周期
L2 命中      → 12~20 个周期
L3 命中      → 40~80 个周期
DRAM 访问    → 100~300 个周期
```

同样的指令条数，实际耗时能差**两个数量级**。软件只能看到"指令流"，看不到"这条指令在等谁"。
PMC 直接给出 `cycles`、`cache-misses`、`stalled-cycles`，把"等"这件事量化出来。

我在 0924 的链表实验里就遇到了这个现象：

| 链表规模 | 每查询探测节点数 | 每探测一个节点耗时 |
| --- | --- | --- |
| 1 000 | 748.83 | 1.6 ns |
| 100 000 | 72 815.21 | 30.3 ns |
| 1 000 000 | 741 602.52 | 132.2 ns |

**同样的循环、同样的指令、只是工作集变大，单次探测的代价涨了 80 倍。**
如果没有 PMC，"为什么慢"这个问题只能靠猜。

#### 原因二：性能问题的重心从"算法"转向"微架构"

现代软件的性能瓶颈大多不在算法复杂度，而在：

- **Cache 缺失 / 访存停顿**（memory wall）
- **分支预测失败**（流水线冲刷）
- **TLB 缺失**（页表遍历）
- **指令级并行不足**（依赖链太长）

这些问题**只有硬件自己知道**。软件层面的 profiler 只能看到"哪个函数耗时多"，
而 PMC 能看到"这个函数为什么耗时多"——是 cache 不友好、还是分支不可预测、还是依赖链太长。

#### 原因三：可观测性（observability）的系统性需求

数据库行业早就验证过这个道理：

- 数据库要调优，必须先有 `pg_stat_statements`、`EXPLAIN ANALYZE`、`pg_stat_bgwriter` 这些统计；
- 操作系统要调优，必须先有 `vmstat`、`iostat`、`perf`；
- CPU 要调优（编译器选参、JIT 选路径、调度器选核），就必须先有 PMC。

**没有测量就没有优化**。PMC 是整条"软硬件协同优化"链路的第 0 环。

#### 原因四：虚拟化与云把"性能隔离"变成了硬需求

在云上，"这台虚机被邻居抢了多少 CPU"必须**可计量**：

- vCPU steal time、超分比、CPU 配额执行情况；
- 容器限流（cgroup CPU bandwidth）是否真的生效；
- 计费（按真实指令数/周期数计费，比按时间计费更公平）。

这些都需要硬件计数器在**硬件层**提供，否则虚拟化层无法证明自己没有"偷"资源。

#### 原因五：硬件成本极低，收益极高

PMC 相对于整个 CPU 的面积，几乎是"零成本"：

- 几十个事件选择器 + 十几个计数寄存器，占不到千分之一的核心面积；
- 但它让编译器、JIT、数据库、操作系统、性能工程师都获得了一个统一的反馈通道；
- 而且**不需要改变指令集**——完全向后兼容，这也是它能普及的关键。

#### 补充：PMC 也是安全能力

PMC 还被用于检测**侧信道攻击**（cache 时序、分支预测器状态）、
检测恶意挖矿/异常负载，这也是它在服务器 CPU 上"必须有"的原因之一。

#### 小结

> 计算越快、越并行、越多级缓存，软件就越"看不见"真实的执行代价。
> PMC 用极小的硬件成本，把"看不见的代价"变成"读得到的数字"，
> 于是它从"发烧友的超频工具"变成了"现代处理器的标配"。

## 三、附加：如果自己实现一个存储引擎，要动哪些地方

课件里给了清晰的"接线位置"，整理成一张表：

| 位置 | 文件 | 要做的事 |
| --- | --- | --- |
| 图 1 | `src/backend/storage/smgr/smgr.c` | 增加内部接口函数（实现 `f_smgr` 里的那些 `smgr_*`） |
| 图 2 | `src/include/storage/smgr.h` | 增加对外调用接口的声明 |
| 图 3 | `src/backend/storage/smgr/smgr.c` | 增加对外接口的实现（如 `smgrread`、`smgrwrite`） |
| 图 4/5 | `src/backend/storage/smgr/md.c`、`md.h` | 增加内部接口的定义与实现 |

关键点：

1. `f_smgr` 是一张**函数指针表**，`smgrsw[]` 数组里 0 号下标初始化的是默认实现（`md`）；
2. `smgr_which` 字段就是"存储管理器选择器"，将来要支持多种引擎，就在这个数组里加一项；
3. `smgr.c` 里的函数都是**静态类型 + 限定作用域**，存储层函数限定在 `smgr.c` 内部，
   外部只看到 `smgr.h` 里的接口——这就是"接口与实现分离"。

也是因为这个结构，PG 后来才能发展出**可插拔的表访问方法**（`CREATE ACCESS METHOD`、
`pg_am`、`tableam` 接口）：接口层稳定了，实现就可以换。
